# Theia Online — Hosting and Operations Requirements

Status: agreed direction, 24 November 2026. Detailed implementation design pending review of each phase. This document specifies requirements, not completed infrastructure.

## Scope and constraints
- Initial private development environment for two testers; use existing AWS account.
- Sydney (ap-southeast-2), EC2 t3a.medium (x86-64, 2 vCPU, 4 GiB). Benchmark sustained simulation, memory and CPU credits before expanding.
- Proposed Ubuntu 24.04 LTS, 40 GiB gp3 EBS, static public IPv4, dedicated network/security group, systemd service and Systems Manager administration. No public SSH by default.
- Single instance for game server and persistence initially; independent managed account authentication; confirm actual database implementation and runtime dependencies from source. No Kubernetes, load balancer or dedicated database initially.
- The `theia-website` repository owns the public site on GitHub Pages, including human-readable release notes, version and platform information, and download links. GitHub Pages also serves the actual launcher and client packages and signed update manifests. Packages are publicly downloadable; access to the hosted realm remains restricted to approved testers.
- `main` includes the trusted local launcher and client installer. Audit these implementations, the Renet account/admission path and PostgreSQL persistence before extending them for hosting.

## Base architecture and long-term scaling (creator-approved)
- Adopt a modular Rust monolith initially on one EC2 instance. Distributed readiness is a formal requirement, not a stretch goal; defer actual distributed deployment until justified by measured demand.
- Establish typed interfaces and explicit state ownership for authentication/login/session and character selection, world coordination, authoritative simulation, social services (chat, friends, guilds, parties), economy (trade, auction house, mail), persistence and administration. Avoid cross-module mutation and process-local assumptions in future service contracts. Keep the independently available gateway/reporting architecture.
- Rust remains the default backend and orchestration language; Go is not required. Luau is the gameplay scripting direction through validated Rust APIs; systemd manages processes, AWS CDK provisions infrastructure and GitHub Actions deploys.
- Establish stable realm, zone, layer, instance, character and server-process identities; distinguish logical ownership from physical addresses. Preserve existing coordinate and authority contracts. Define routing and handoff interfaces with local implementations initially; future transfers require authenticated destination readiness, ownership fencing, retry/recovery and reconnect semantics. Never permit simultaneous authoritative ownership of a character. Persistence must survive process replacement.
- Economy and inventory operations must be atomic, durable, auditable and idempotent, preventing item duplication or loss across retries and crashes. No separate database per module initially.
- Long-term: independently extract login, chat/social, economy/auction house, persistence and world coordination services when capacity or availability warrants. Define cross-zone/layer social and economy scope before extraction.
- World coordinator manages player allocation, zone ownership, population layers and private instances where game design permits; preserve party cohesion, PvP rules and world continuity. Infrastructure controller manages host/process capacity and health. Generic load balancing does not replace game-aware routing.
- Scale from multiple processes on one host to multiple hosts after profiling and load tests. Collect per-process/zone population, tick latency, CPU/memory, network and persistence metrics. Define capacity thresholds, hysteresis, draining and recovery before automatic scaling.
- Phase 1 design gate: audit existing module boundaries, identity/authority and persistence contracts; introduce only foundations needed now. Later distributed implementation requires explicit design review and tests for handoff, recovery, duplicate prevention and cross-service behavior.

## Separation of concerns — engineering policy (creator-approved)
- Prioritize reviewing the existing networking crate's simulation responsibilities. Progressively move authoritative world state, physics, combat and NPC behavior behind a simulation boundary; networking owns connections, transport, protocol encoding and replication delivery. Simulation owns authoritative outcomes and exposes typed commands/events/snapshots; shared contracts remain transport-independent. Avoid circular dependencies.
- Keep gameplay independent of AWS and deployment APIs; infrastructure integrates through adapters. Authentication remains independent of gameplay, with explicit session/admission contracts. Persistence uses asynchronous bounded workers and must not block the simulation tick; preserve durable acknowledgement and ownership guarantees.
- New chat, guild, party, trade and auction-house features must define state ownership, interfaces and transaction/consistency requirements before implementation. Luau scripts use controlled, validated gameplay APIs rather than direct database, transport or infrastructure access.
- Preserve existing core, auth and persistence boundaries. Audit dependencies before extracting a simulation crate; use incremental, tested changes rather than a wholesale rewrite. Maintain existing protocol compatibility where required, gameplay behavior and regression tests. Document exceptions and migration steps.
- Treat separation as an ongoing design/review criterion, not a requirement to deploy separate processes now. Keep the initial single-server deployment and avoid delaying gameplay for speculative refactoring.

## Initial hosting scope and cost priority (creator-approved, supersedes earlier phase scheduling)
- Minimize recurring costs for two testers. Phase 1 provisions only essential EC2 t3a.medium, Ubuntu 24.04, encrypted persistent EBS, necessary networking/IAM and local PostgreSQL/systemd, plus independent account authentication and the minimal on-demand gateway below. Retain AWS CDK and manual release/deployment policy. No dedicated database, load balancer, NAT gateway or always-running proxy.
- Bring the minimal Theia Gateway and automatic idle shutdown forward from Phase 2 into Phase 1 as cost-saving requirements. Use AWS API Gateway HTTP API (not REST API or Lambda Function URL) with a small Rust Lambda for authenticated status/wake requests, scoped to the designated EC2 instance. Rate-limit requests; no embedded AWS credentials or gameplay traffic through gateway.
- Launcher Play wakes the instance and waits for actual game/database readiness; use bounded polling, idempotent start, pending-join/reconnect protection and coordinated lifecycle transitions. Use one DynamoDB table for conditional updates to realm lifecycle state, boot and release identity, maintenance and expiring join reservations. The game server owns the connected player count. After five idle minutes, stop EC2 only after confirmed persistence flush; leave the instance running on flush failure. A Play request after drain commits waits for the next boot. Retain manual controls and maintenance override. Deployment restores the prior stopped state only when no player demand exists.
- Phase 1 retains basic local structured logs, essential security, persistent data and graceful shutdown. Defer CloudWatch integration/custom metrics, automated backups/snapshots, advanced monitoring, advanced budget automation, centralized error/bug collection and dashboard to a later development/production-readiness cycle. These remain long-term requirements; earlier phase gates referring to deferred features are postponed accordingly. Local persistent storage is not a backup; explicitly accept development data-loss risk until backups are introduced.
- Stopped EC2 avoids compute charges, not EBS/public IPv4 or gateway/request charges. Review estimated recurring costs before provisioning; avoid unnecessary paid services. Phase 1 acceptance includes remote two-player play, manual release/deploy, persistence across stop/start, authenticated wake/readiness and safe idle stop.

## Infrastructure tooling decision (creator-approved)
- AWS CDK in TypeScript replaces Terraform as the infrastructure-as-code tool throughout this document. CloudFormation manages stack state; no Terraform state bucket or locking infrastructure is required.
- Use infrastructure/aws for CDK stacks and configuration, with pinned dependencies, synthesis and validation in CI, and manually approved infrastructure deployment/destruction. Reuse appropriate patterns from Projex without sharing application resources or credentials.
- Bootstrap CDK only as needed; account for deployment asset storage and any other bootstrap resource charges. Keep game release deployment independent of infrastructure changes. Rust remains the game server and Lambda implementation language.

## Phase 1 — Foundation and manual operations
- Version-controlled infrastructure as code (AWS CDK proposed under infrastructure/aws), with CloudFormation-managed state, least-privilege roles, resource tags and budget alerts. Review plan before provisioning paid resources.
- Reproducible, locked builds for Linux server and supported client/launcher platforms; reuse existing scripts and asset preparation. Build on CI runners, not EC2. Ensure server package includes required world/collision data and can run headless.
- Separate CI validation, server deployment, client publishing and launcher publishing workflows under .github/workflows. Manual release/deploy triggers initially; commits must not restart the server. Pin dependencies/actions, use GitHub OIDC and scoped AWS roles, no long-lived AWS keys in repository or client.
- Immutable versioned artifacts, manifests, integrity checks (SHA-256 and signed release metadata), protocol/content compatibility checks, atomic installation and rollback. Publish manifests only after packages are available. Preserve compatible server/client release sets.
- Deploy via Systems Manager or equivalent authenticated mechanism; graceful drain, local backup before every deployment requiring migrations, health checks and rollback to last known good release. Database rollback must respect schema compatibility.
- Verify remote networking, bind/advertised addresses, secure authentication, certificate/token handling and persistence before exposing the server. Restrict network access to required ports and testers where practical. No public database.
- Manual start/stop/restart via AWS console initially. systemd starts game service on boot and handles unexpected process failure. Persist data across EC2 stop/start; encrypted storage and tested local pre-migration restore; off-site and scheduled backups deferred.
- Phase 1 observability: bounded local structured Rust logs, readiness and health checks, build IDs and non-secret correlation IDs. CloudWatch integration, custom metrics and centralized monitoring are deferred. Never log credentials or bearer tokens.

## Phase 1 platform and modular release packaging (creator-approved)
- Linux only for server, client and launcher initially; generic x86-64, Ubuntu 24.04 LTS build/server baseline, Linux Mint 22 on AMD CPU/GPU as primary client qualification platform. Pin existing Rust toolchain and dependencies; validate Vulkan/Mesa and runtime libraries. Headless server must not require desktop/GPU.
- Independently version server, client executable and launcher releases. Preserve launcher self-update behavior; audit current local implementation before changes. Prefer compressed user-installable archives initially.
- Replace whole-client updates with manifest-based package-level patching in Phase 1. Independently version client executable, UI, character/equipment/animation assets, world objects, terrain by zone/region, audio and client-facing gameplay content. Final package boundaries follow actual dependencies and asset layout; keep authoritative server-only data private.
- Serve signed release manifests and immutable package URLs directly from GitHub Pages. Manifest specifies release/protocol compatibility, package IDs, versions, dependencies, sizes, URLs and SHA-256 hashes. Verify all referenced files before activating the manifest. Check the complete Pages artifact, including the site and retained rollback packages, against Pages limits and verify redistribution rights before publishing. If it does not fit, reduce package size or request a distribution review. Game downloads do not use S3 or GitHub Release assets.
- Launcher compares installed package inventory with approved manifest, downloads only missing/changed packages, verifies signatures and hashes, stages and validates a complete compatible release before atomic activation. Preserve previous playable release on interruption/failure; handle removed packages, disk space, concurrent launch/update and rollback. Routine game updates require no administrator privileges. The launcher's own Debian package update retains desktop APT approval for Phase 1.
- Package-level replacement first; binary delta patching deferred until justified. Acceptance: clean install, executable-only update, single terrain-package update, launcher self-update, corrupted/interrupted download rejection and rollback, compatible remote multiplayer on Mint 22. No unrelated assets should be downloaded for an isolated package change.

## Release versioning and channels (creator-approved)
- Development is the active channel and default for initial testing; Stable is reserved for explicitly approved known-good releases and may remain empty for an extended period. Stable does not imply production readiness.
- Independently version launcher, client, server and asset packages; record immutable build identifiers and Git commit SHA. Track network protocol and content/schema compatibility separately. A signed release manifest identifies the exact compatible artifact set.
- Maintain separate channel manifests and launcher channel selection; handle unavailable Stable gracefully. Promote the exact tested immutable artifacts from Development to Stable without rebuilding. Manual publishing, promotion and server deployment via GitHub Actions initially.
- One hosted game environment and one active server release initially; two channels do not imply two live worlds. Validate client/server compatibility before Play and clearly report mismatches. Preserve prior release artifacts for rollback, subject to database/schema compatibility.
- No requirement to publish a Stable release during Phase 1; qualify the promotion mechanism without exposing unapproved builds as Stable.

## CI/CD trigger policy (creator-approved)
- Automatic CI validation on pushes and pull requests. Use the full PR matrix when a branch has an open PR, retain push validation for standalone branches and `main`, and avoid duplicate push and PR matrices for the same change. Build release candidates automatically on pushes to `main`. Detect affected server, client, launcher and asset packages using dependency-aware change detection, including shared crates, lockfiles, toolchain and build configuration; fall back to full builds when uncertain.
- Separate reusable server, client and launcher build workflows, CI validation, manual publish and manual AWS deploy workflows; provide a manually triggered combined release workflow. Build candidates are immutable and traceable to commit, with compatible artifact sets and retained rollback candidates.
- Publishing game packages and manifests to GitHub Pages, Stable promotion and AWS deployment remain explicitly manual. A regular website build must preserve the currently approved downloads and manifests. No successful build or push may automatically change a live release or restart the server. Failed or incomplete builds cannot publish. Serialize publication/deployment, cancel superseded unneeded builds safely, and verify compatibility and health before activation.
- Future idle-window automatic Development publishing/deployment is deferred pending explicit approval and lifecycle safeguards.

## Lifecycle (Phase 1) and reporting (Phase 2)
- Independently available Theia Gateway using API Gateway and Lambda. Authenticated player wake/status requests; admin permissions separate. Rate limit and make wake requests idempotent. No gameplay traffic through gateway.
- Launcher Play requests wake automatically if stopped, polls status and launches client only after application readiness. States: offline, starting, ready, draining/shutting down, failed; distinguish EC2 running from game/database readiness. Return validated connection endpoint. Provide timeout/retry and useful errors.
- Zero connected players triggers proposed five-minute idle grace period. Pending joins/reconnect reservations prevent shutdown. Serialize wake/drain transitions, handle concurrent requests and boot failure; save/flush persistent data before stopping EC2 (not merely exiting the game process). Provide maintenance override and manual fallback. Avoid stop/start loops. Compute stops billing while stopped; storage, IPv4 and other retained resources may still cost money.
- Collect server and client errors/crashes, including launcher failures where practical. Reporting endpoint remains available while EC2 is offline. Local bounded queue for offline submissions; retry with deduplication and rate/size limits.
- In-game Report Bug: description, optional screenshot with consent, zone/location, relevant diagnostic state, recent sanitized logs, client/server versions, correlation ID and timestamp. Preview/redact sensitive data; exclude credentials, tokens and unrelated personal data. Crash diagnostics best effort and consent-aware.
- Proposed DynamoDB report metadata and private S3 attachments, with scoped access, encryption, retention/deletion and upload validation. CloudWatch for operational telemetry. Define schemas, quotas and cost limits before implementation.

## Phase 3 — Administration panel
- Separate static web UI (GitHub Pages proposed), available when game instance is stopped. Actual authorization enforced by authenticated API, not by hiding the static page. No embedded privileged credentials. Role-based access, admin audit trail, confirmation for destructive actions.
- Infrastructure: EC2 lifecycle, CPU/credits, memory, disk, network, uptime, running hours and AWS costs (billing data may lag).
- Game: readiness, connected players, tick performance, entities, latency, build and database health/last backup. Clearly label stale/unavailable metrics when stopped.
- Controls: start, graceful stop, restart, maintenance override; deployment/version history, approved release selection and rollback.
- Errors: searchable server/client/launcher events, crash grouping, severity, correlation, recent logs and trends.
- Bug reports: searchable queue, attachments, status, priority, investigation notes, optional GitHub Issues integration with explicit action and sanitized content.
- Use shared gateway/API contracts with separate player and administrator authorization. Admin operations must not expose AWS credentials to browser.

## Acceptance gates and open design decisions
1. Phase 1: reproducible CI artifacts; manual deployment and rollback; two remote clients connect securely; data survives restart; local pre-migration restore and bounded logs verified; authenticated wake, readiness, concurrent joins and safe five-minute idle stop tested.
2. Phase 2: offline/error/bug reports arrive without game server running; advanced monitoring and scheduled/off-site backups introduced after review.
3. Phase 3: authorized admin can inspect health, manage lifecycle and releases, correlate errors and triage reports; unauthorized users cannot perform privileged operations.
- Review exact ports, database engine, authentication, release manifest schema, asset packaging, AWS CDK state/bootstrap, DNS/TLS, IAM, idle policy, telemetry schema/retention, budget and dashboard technology during detailed phase design.
- No AWS resources or workflows are provisioned by this requirements document. Implement only after phase-specific review.

## AWS CDK bootstrap preflight
- Before provisioning, inspect the existing AWS account in ap-southeast-2 (Sydney) for the CloudFormation CDKToolkit stack and its S3 deployment asset bucket (standard name begins cdk-hnb659fds-assets).
- Verify account/region, bootstrap version, qualifier, deployment roles, trust and permissions, bucket security/encryption and compatibility with Theia's CDK synthesizer. Reuse the existing bootstrap resources if suitable; otherwise bootstrap only after review and approval. Do not modify or delete shared Projex assets.
- Generate deployment assets from version-controlled source as needed; retain assets referenced by deployed stacks or required for rollback. Review safe garbage collection of obsolete assets, including versions, without disrupting other projects. No separate Terraform state bucket or game-data bucket is required.
- Status: read-only Sydney preflight verified CDKToolkit v32, its default qualifier and a private, KMS-encrypted asset bucket. The shared CloudFormation execution role has administrative permissions. The initial host stack synthesizes and its template validated in Sydney. Review deployment identity, required parameters and cost before provisioning. See [the AWS runbook](../../infrastructure/aws/README.md).

## EC2 runtime and database migration policy (creator-approved)
- Install immutable versioned server releases with an atomic active-release pointer; separate configuration/secrets, PostgreSQL persistent data and bounded local journal logs from release directories. Run game server as a dedicated unprivileged user.
- Separate systemd services for PostgreSQL and game server; verify database readiness, configuration, world assets and schema compatibility before accepting players. Bounded crash restarts; graceful drain and persistence flush on intentional stop. Support independent game restart, database restart and host reboot.
- Automatically execute version-controlled PostgreSQL migrations as part of each approved deployment, before activating the new server, not on ordinary service startup. Serialize migrations, validate expected schema and use transactions where supported. Stop deployment on failure and report diagnostics; retain previous artifacts. Restart previous release only if schema remains compatible; otherwise remain in maintenance for explicit recovery. No destructive or irreversible migration without explicit review and a recovery plan; deferred automated backups do not remove this safeguard.
- Inspect and reuse existing persistence migration machinery rather than introducing a competing migration system. Qualify successful migration, failed migration, repeated deployment and restart without migration.


## Phase 1 — Authentication, configuration and secrets
- Keep account authentication available while EC2 is stopped. Use Cognito managed browser sign-in from the launcher with OIDC authorization code flow and PKCE for the private hosted playtest. Retain the native Keycloak flow for local development. Disable public registration and manually provision the two testers. Require scoped access tokens and tester authorization before wake; keep admin permissions separate. Once the realm is ready, pass a short-lived session to the client in memory for native character selection. Link issuer/subject identity to the PostgreSQL account and issue Renet admission tickets only after server-side ownership and compatibility checks. Defer public registration, verification and recovery workflows.
- Version-control non-secret configuration templates; keep environment-specific configuration outside releases. Use encrypted standard-tier Systems Manager Parameter Store for credentials and signing secrets where appropriate; review KMS/API costs. Scope EC2, Lambda and GitHub OIDC roles independently; no permanent AWS keys in clients or repository.

## Phase 1 — Launcher lifecycle and release trust
- States: Offline, Starting, Initialising, Ready, Shutting Down, Maintenance and Error. Play requests wake only after compatible updates are installed; opening launcher or downloading updates never wakes EC2. Poll every five seconds with configurable five-minute startup timeout. Wait for shutdown completion before requesting restart; serialize concurrent requests. Block Play in maintenance; provide useful errors and safe retries.
- Five-minute idle timer begins after last player and pending join leave; cancel on authorized join. Developer-only keep-alive override with automatic expiry (30 minutes, one, two or four hours), display remaining time. Maintenance prevents idle shutdown during deployment. Bound startup failures and safely stop failed idle instances unless maintenance or explicit override requires retention.
- Maintain independently accessible deployed-server version record, distinct from published release candidates. Validate client, launcher minimum version, protocol and asset compatibility before wake and independently on server admission. Resume interrupted package downloads; preserve previous installation on failure.
- Sign release manifests with Ed25519 private key held in protected GitHub Actions publishing environment; embed trusted public keys in launcher. Verify signature and SHA-256 package hashes before activation. Support multiple trusted keys during manual rotation and document compromise recovery; reject invalid signatures and unauthorized rollback.

## Phase 1 — Recovery, administration and cost controls
- Before every deployment requiring schema migrations, drain game writes and create a local PostgreSQL dump on encrypted persistent EBS; validate backup success before migration. Encrypt sensitive backups, protect keys outside repository, retain a small bounded number with disk-space limits. Test restoration; local backup does not protect against volume loss. Scheduled and off-site backups remain deferred.
- Retain current and previous server releases; rollback only when schema compatible, otherwise remain in maintenance for explicit recovery. Separate infrastructure IAM permissions from game deployment permissions. Use Systems Manager Session Manager and Run Command; no public SSH. PostgreSQL local only.
- Distinguish running, ready and healthy. Bound systemd crash retries, rotate local logs, report deployment failures via GitHub workflows. No paid monitoring platform required initially. Configure basic AWS budget email alerts at 50%, 80% and 100% of agreed monthly target; alerts are not spending caps. Confirm target and costs before provisioning.
- Provide lightweight admin CLI on Linux Mint: status (instance, health, deployed version, player count, idle countdown), start/graceful stop, independent game restart, maintenance, expiring keep-alive, recent logs via SSM, deployment and rollback workflow triggers. Confirm actions disconnecting players. Reuse operation contracts for future dashboard; no permanent credentials.
- Maintain concise repository runbook for deploy, rollback, logs, restart, failed migrations and troubleshooting launcher/server/database/infrastructure.

## Phase 1 implementation milestones and acceptance
1. Repository audit: inventory existing auth, launcher, networking, persistence, packaging and workflows; reconcile local changes; identify reuse, gaps and dependencies. Audit is the first implementation gate.
2. Build/release: automatic CI and candidates, independent versions, modular packages, signed manifests, manual publish/deploy; test interrupted/corrupt updates and compatibility.
3. AWS preparation: verify Sydney bootstrap reuse, scoped OIDC roles, budget target and alerts; review cost and obtain explicit provisioning approval.
4. Infrastructure: reproducible CDK synthesis and approved CloudFormation deployment of EC2/EBS/network/IAM, Cognito, HTTP API, Rust Lambda and the lifecycle table.
5. Runtime: first rehearse one headless release with manual start and graceful systemd stop on Ubuntu 24.04. Verify two-player admission, progress after restart, deployment-only migrations, startup schema checks, failed migration and local restore, and bounded logs before automating wake and idle stop.
6. Launcher/gateway: test tester-only login while offline, unauthorized wake rejection, simultaneous requests, compatibility before wake, readiness, timeout, five-minute idle stop and expiring override.
7. Deployment/admin: test manual deployment, compatible rollback, migration failure handling, maintenance, CLI and runbook.
8. Remote acceptance: two testers authenticate, update, wake, play together, disconnect, observe EC2 stop after five idle minutes, reconnect with character progress intact. Verify no unauthorized startup or data loss.
- Track each milestone with dependencies, tests, evidence and completion status. Complete local development/testing before paid provisioning wherever possible. Reuse existing code, avoid speculative dependencies and deferred features. No AWS provisioning without explicit approval. Requirements are not evidence of implementation; audit and checklist tracking precede coding.
