# Modular hero and character creation

Adopted by the user on 22 November 2026: use the owned Modular Fantasy Hero
Characters package for players, add character customization, persist appearance
and show it to other players. Work autonomously in local commits; native mouse
and display use is authorized. P2-08/P2-09 presentation and P3-03 character creation.

The source package is `/home/steven/Downloads/Synty Models/Characters/Models/Modular
Fantasy Hero Characters - v1.3.2.unitypackage`. Payloads and converted art remain
outside Git under ignored build directories. Read Unity serialization as data;
never execute supplied scripts. Standard Bevy meshes, skinning, animations,
materials and UI remain the rendering path.

The initial catalogue has two bodies, four heads per body, bald/four hair styles,
none/three male facial-hair choices, four skin tones, four hair colours and two
outfits. Body changes clear incompatible facial hair. These are cosmetic choices;
they do not change collision, movement, combat stats or equipment ownership.
The outfits are starter appearances, not an equipped-item implementation.

`theia_core::appearance::Appearance` is the bounded catalogue contract, with
versioned strict JSON and fixed seven-byte values. It rejects unknown fields,
unsupported indices and incompatible combinations. Stable part names and palette
paths are generated by trusted code, never supplied as arbitrary client paths.

Planned slices and acceptance:

1. Convert a curated modular skin and existing qualified clips, preserve bind
   axes and weapon sockets, inspect actual animated GLB rendering and record
   numerical conversion checks. Keep the previous player available as fallback.
2. Persist appearance atomically with character creation, validate ownership at
   list/select/admission and prove actual database restart and rollback behavior.
3. Carry server-owned appearance through bounded public player metadata; test
   malformed/stale metadata, reconnect and distinct appearances for two players.
4. Add a native rotating character preview and customization controls to the
   existing account creation/selection flow; validate save/enter/reload with the
   same character in the live Millhaven playtest.

Verification results and completed slice scope will be recorded below. A planned
screen or a successful conversion alone does not establish persistent multiplayer.

Implemented persistence and public metadata (22 November 2026):

- Migration 15 adds constrained seven-byte appearance to the character row;
  older rows get the default. Creation stores name and appearance together.
  Account list/select and the authenticated admission lease carry saved choices.
- Public player metadata is PN02 (maximum 341 bytes, eight actors), with gameplay
  wire version 14 reflected in the authenticated transport protocol ID. Both binaries
  must be updated together; PN01 is not accepted as PN02. Gameplay input cannot
  submit a mesh path or override another actor's saved appearance.
- Owned PostgreSQL character contract passed, including ownership, name/quota
  rollback, invalid appearance SQL constraints and upgrading the old schema.
  A nondefault appearance survives process/database restart and list/select.
  Evidence: `build/modular-hero-v1/database-v2/`.
- Seven bounded identity codec tests passed. The real encrypted two-peer
  equipment/admission test also verifies distinct appearances at both receivers
  through delay, jitter, loss and duplication (`two-peers.log`). Its admission
  policy is synthetic; SQL durability is established separately above.

Implemented asset conversion:

- `tools/convert_modular_hero.py` reads four named data payloads from the owned
  Unity package, generates 16 standard texture palettes, and exports a curated
  57-part variant GLB plus a 13-part default GLB. There are 65 skin joints,
  at most three weights per vertex and all 22 qualified locomotion/combat clips.
  Converted files and extracted licensed source remain ignored local artifacts.
- Animation transfer preserves the target bind axes. Applying source absolute
  bone poses directly produced invalid deformation and was rejected. The final
  conversion applies source deformation relative to each target bind matrix;
  measured maximum baked world-pose error is below 0.00002.
- `build/modular-hero-v1/art-v3` was inspected as actual animated Bevy output:
  native editor idle, walking and jumping captures are in `native-asset/`.
  Native character creation also rendered the female alternate outfit and palette
  in `native-creation/fresh/custom-character.png`. Individual combat clips have
  conversion checks; this is not a claim of a complete visual combat audit.
- Native Linux device: AMD Radeon RX 7900 XTX (RADV NAVI31), Vulkan,
  Mesa 26.2.7. Windows native rendering has not been exercised in this slice.

Implemented native creation and presentation:

- The editor's **Zone → Start account population playtest…** opens a native
  character picker after login. Empty accounts can customize body, face, hair,
  facial hair, skin tone, hair colour and starter outfit, rotate an animated
  preview, enter a name and create. Existing characters preview their saved look;
  select a row then **Enter selected character**. Incompatible facial-hair controls
  and Enter without a selection are disabled. Cosmetic changes create a new draft;
  this slice does not add editing of an existing character's appearance.
- Preview and gameplay use the same curated part selection and immutable cached
  palette materials with standard Bevy skinning. Preview has its own render layer
  and camera. Initial visibility waits for parts and palette texture readiness.
  Local and remote players bind choices to their current authoritative actor.
- The private account handoff carries validated appearance on creation and in the
  roster, retaining legacy default appearance when omitted. Selection allows ten
  minutes. No private identity or asset pathname is sent as public player metadata.
- `native-creation-v3/qualification.json` passes actual native creation, invalid
  name refusal, rotated preview, Millhaven entry, two authenticated clients seeing
  both distinct appearances, editor Stop, database restart, roster preview and
  both clients entering again. Source zone bytes remain unchanged. Captures include
  `fresh/custom-character.png` and `fresh/guest/two-heroes.png`.
- The forced Vulkan validation layer reports one known initial surface-size race
  per editor launch (VUID-VkSwapchainCreateInfoKHR-pNext-07781). This is counted by
  the existing narrow qualification exception; there are no other GPU/UI errors.
  This is functional native evidence, not a performance measurement. Main editor
  capture: 3440×1440; second player: 1720×1400. Smaller-window layout is not qualified.
- Local launch defaults prefer `build/modular-hero-v1/art-v3` when present and
  retain the earlier POLYGON art fallback. Offline F5 uses the default hero;
  saved customization belongs to the account playtest. The local editor wrapper
  uses disposable account services, as before; production launcher/title screens,
  long-lived deployment accounts and equipped-item visual swaps remain separate.
